# راهنمای مدرس — هوک‌ها در Claude Code و Codex

مدت: ۱۲۰ دقیقه؛ زمان اختصاصی هر اسلاید در زیر آمده است. فعالیت‌های عملی در زمان همین اسلایدها انجام می‌شوند، نه علاوه بر آن. پیش از کلاس نصب ابزارها را طبق راهنمای آزمایشگاه انجام دهید.

در صورت نیاز به استراحت، پنج دقیقه از بخش بحث پایانی کم کنید و آن را در زمان جلسه ثبت کنید.

## 1. هوک چیست؟ تو صدا نمی‌زنی، سیستم صدا می‌زند — دقیقهٔ 0 تا 5

- هوک نقطه‌ای از پیش تعیین‌شده در چرخهٔ کار یک سیستم است که کد تو به آن وصل می‌شود
- هر بار سیستم به آن نقطه برسد، خودش کد تو را اجرا می‌کند؛ لازم نیست کسی یادش بماند
- مثال آشنا: pre-commit در Git پیش از هر commit اجرا می‌شود و اگر شکست بخورد commit انجام نمی‌شود

**راهنمای اجرا و بحث:** با Git hook شروع کنید چون بیشتر فراگیرها دیده‌اند. بپرسید چه کسی pre-commit را اجرا می‌کند؛ پاسخ این است که خود Git، نه برنامه‌نویس. جملهٔ کلیدی جلسه را روی تخته بنویسید: «تو صدا نمی‌زنی، سیستم صدا می‌زند.» هنوز وارد Claude و Codex نشوید؛ فقط مفهوم نقطهٔ قلاب و اجرای خودکار را جا بیندازید.

## 2. حلقهٔ کار عامل و نقطه‌های قلاب — دقیقهٔ 5 تا 10

- عامل در حلقه کار می‌کند: پیام، فکر، فراخوانی ابزار، نتیجه و در نهایت پایان
- هر مرحلهٔ این حلقه یک رخداد است که می‌شود به آن هوک وصل کرد
- پنج رخداد پرکاربرد: SessionStart، UserPromptSubmit، PreToolUse، PostToolUse و Stop

**راهنمای اجرا و بحث:** نمودار را از راست به چپ دنبال کنید. توضیح دهید PreToolUse و PostToolUse برای هر فراخوانی ابزار یک بار اجرا می‌شوند، ولی SessionStart یک بار در هر نشست و Stop یک بار در پایان هر نوبت. Claude Code رخدادهای بیشتری مثل Notification، PreCompact و SubagentStop دارد؛ امروز روی همین پنج رخداد مشترک با Codex تمرکز می‌کنیم.

منابع: [مرجع هوک در Claude Code](https://code.claude.com/docs/en/hooks)، [مرجع هوک در Codex](https://learn.chatgpt.com/docs/hooks)

## 3. خواهش یا قانون؛ دستورالعمل در برابر هوک — دقیقهٔ 10 تا 15

- AGENTS.md و Skill را مدل می‌خواند و ممکن است فراموش یا نادیده بگیرد
- هوک را خود میزبان اجرا می‌کند و مدل نمی‌تواند از آن رد شود
- AGENTS.md و Skill از مدل خواهش می‌کنند؛ هوک اجرا را تضمین می‌کند.

**راهنمای اجرا و بحث:** این مهم‌ترین اسلاید مفهومی جلسه است و به جلسهٔ قبل وصل می‌شود. مثال بزنید: جملهٔ «پیش از پایان تست‌ها را اجرا کن» در AGENTS.md یک خواهش است؛ هوک Stop که تست را اجرا می‌کند یک قانون است. قاعدهٔ انتخاب: هرچه سبک، زمینه یا روش کار است در دستورالعمل بماند؛ هرچه حتی یک بار نباید نقض شود به هوک برود.

**دستورالعمل متنی یا هوک اجرایی؟**

| موضوع | AGENTS.md و Skill | Hook |
| --- | --- | --- |
| چه کسی اجرا می‌کند؟ | مدل می‌خواند و تفسیر می‌کند | خود میزبان اجرا می‌کند |
| قطعیت | ممکن است فراموش یا نادیده گرفته شود | هر بار، بدون استثنا |
| زبان | متن طبیعی | کد: اسکریپت یا فرمان shell |
| مناسب برای | سبک، زمینه و روش انجام کار | قاعده‌ای که حتی یک بار نباید نقض شود |
| مثال | «پیش از پایان تست‌ها را اجرا کن» | هوک Stop که تست‌ها را اجرا می‌کند |

منابع: [مرجع هوک در Claude Code](https://code.claude.com/docs/en/hooks)، [مرجع هوک در Codex](https://learn.chatgpt.com/docs/hooks)

## 4. هوک کجا وجود دارد؟ ابزار محلی، نه چت وب — دقیقهٔ 15 تا 19

- Claude Code و Codex روی سیستم تو فایل می‌خوانند، فرمان اجرا می‌کنند و هوک دارند
- ChatGPT و claude.ai در مرورگر روی سیستم تو چیزی اجرا نمی‌کنند و هوک کاربر ندارند
- هوک خودکار فعال نمی‌شود؛ تا در فایل تنظیمات تعریف نشود وجود ندارد

**راهنمای اجرا و بحث:** خیلی از فراگیرها چت وب و ابزار کدنویسی را یکی می‌دانند؛ این تفکیک را صریح بگویید. هیچ هوک پیش‌فرضی همراه ابزار نمی‌آید، ولی پلاگین‌ها می‌توانند هوک همراه خود بیاورند؛ پس با نصب یک پلاگین ممکن است هوکی فعال شود که خودتان ننوشته‌اید. این نکته را برای بخش امنیت نگه دارید.

## 5. چهار نقش هوک — دقیقهٔ 19 تا 24

- نگهبان، خودکارساز، بازخورددهنده و زمینه‌ساز
- هر نقش به رخداد مشخصی بیشتر می‌خورد
- هوک‌ها را با کاری که می‌کنند بشناسید، نه با نام رخداد.

**راهنمای اجرا و بحث:** جدول را نقش‌به‌نقش بخوانید و برای هر نقش از کلاس یک مثال از پروژهٔ خودشان بخواهید. بقیهٔ جلسه دقیقاً با همین چهار نقش جلو می‌رود: اسلاید نگهبان، خودکارساز، حلقهٔ بازخورد و زمینه‌ساز. اگر فراگیری بپرسد یک هوک می‌تواند چند نقش داشته باشد، پاسخ مثبت است؛ ولی هوک کوچک و تک‌منظوره راحت‌تر آزمون و اشکال‌زدایی می‌شود.

**هر هوک به یک سؤال جواب می‌دهد**

| نقش | سؤال | رخداد معمول | مثال |
| --- | --- | --- | --- |
| 🛡️ نگهبان | اجازه بدهم این کار انجام شود؟ | `PreToolUse` | قفل dist و .env |
| ⚙️ خودکارساز | بعد از این کار چه خودکار انجام شود؟ | `PostToolUse` | فرمت با Prettier |
| 🔁 بازخورددهنده | نتیجه درست بود؟ اگر نه، به مدل بگو | `PostToolUse`، `Stop` | lint و build |
| 📋 زمینه‌ساز | مدل پیش از شروع چه باید بداند؟ | `SessionStart` | شاخه و وضعیت Git |

منابع: [مرجع هوک در Claude Code](https://code.claude.com/docs/en/hooks)، [مرجع هوک در Codex](https://learn.chatgpt.com/docs/hooks)

## 6. رخدادهای اصلی در Claude Code و Codex — دقیقهٔ 24 تا 29

- نام و منطق رخدادهای اصلی در هر دو ابزار یکسان است
- جزئیات خروجی و پشتیبانی هر نسخه متفاوت است
- نام و منطق رخدادهای اصلی در هر دو ابزار یکسان است؛ جزئیات را با نسخهٔ نصب‌شده بسنجید.

**راهنمای اجرا و بحث:** نکتهٔ مثبت برای کلاس: یاد گرفتن هوک در یک ابزار تقریباً مستقیم به دیگری منتقل می‌شود. تفاوت‌های مهم را بگویید: PreToolUse در Codex فعلاً تصمیم ask ندارد و فقط allow یا deny می‌دهد. Codex در خروجی Stop با exit 0 حتماً JSON می‌خواهد. Claude Code حدود سی رخداد دارد؛ فهرست کامل را از مرجع رسمی نشان دهید، حفظ کردنش لازم نیست.

**پنج رخداد مشترک؛ ✓ یعنی پشتیبانی در مستند رسمی**

| رخداد | کی اجرا می‌شود؟ | Claude Code | Codex |
| --- | --- | --- | --- |
| `SessionStart` | شروع یا ادامهٔ نشست | ✓ stdout به زمینه می‌رود | ✓ stdout به زمینه می‌رود |
| `UserPromptSubmit` | ارسال پیام کاربر | ✓ رد پیام یا افزودن زمینه | ✓ رد پیام یا افزودن زمینه |
| `PreToolUse` | پیش از اجرای ابزار | ✓ allow، deny یا ask | ✓ allow یا deny؛ ask هنوز نه |
| `PostToolUse` | پس از اجرای موفق ابزار | ✓ بازخورد به مدل | ✓ بازخورد به مدل |
| `Stop` | وقتی عامل می‌خواهد تمام کند | ✓ ادامهٔ اجباری | ✓ ادامهٔ اجباری؛ JSON در exit 0 |

منابع: [مرجع هوک در Claude Code](https://code.claude.com/docs/en/hooks)، [مرجع هوک در Codex](https://learn.chatgpt.com/docs/hooks)

## 7. ساختار تنظیم: رخداد، matcher و فرمان — دقیقهٔ 29 تا 34

- هر هوک سه لایه دارد: رخداد، matcher که ابزار را انتخاب می‌کند و handler که فرمان را اجرا می‌کند
- matcher نام ابزار یا regex است و Edit و Write را با یک الگو هم‌زمان انتخاب می‌کند
- Codex ابزار apply_patch را با نام‌های Edit و Write هم تطبیق می‌دهد؛ پس یک matcher در هر دو کار می‌کند

**راهنمای اجرا و بحث:** نمونه را لایه‌لایه از بیرون به داخل بخوانید: کلید hooks، نام رخداد، آرایهٔ گروه‌ها با matcher، و آرایهٔ handlerها. timeout برحسب ثانیه است. برای Stop و UserPromptSubmit matcher معنا ندارد و نادیده گرفته می‌شود. یادآوری کنید ساختار JSON در Claude Code و Codex یکسان است؛ همین شباهت در آزمایشگاه اجازه می‌دهد یک پوشهٔ اسکریپت برای هر دو ابزار داشته باشیم.

```text
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {"type": "command", "command": "node hooks/feedback.mjs", "timeout": 30}
        ]
      }
    ]
  }
}
```

منابع: [مرجع هوک در Claude Code](https://code.claude.com/docs/en/hooks)، [مرجع هوک در Codex](https://learn.chatgpt.com/docs/hooks)

## 8. ورودی هوک: JSON روی stdin — دقیقهٔ 34 تا 38

- میزبان جزئیات رخداد را به شکل JSON به ورودی استاندارد اسکریپت می‌دهد
- فیلدهای مشترک: session_id، cwd، hook_event_name، tool_name و tool_input
- شکل tool_input به ابزار بستگی دارد: Claude برای Edit مسیر file_path می‌دهد، Codex متن patch را در command

**راهنمای اجرا و بحث:** این اسلاید دلیل وجود فایل lib.mjs در آزمایشگاه را توضیح می‌دهد. اسکریپتی که فقط file_path را بخواند در Claude کار می‌کند ولی در Codex هیچ فایلی نمی‌بیند، چون apply_patch مسیرها را داخل متن patch با سرخط Update File می‌فرستد. پس اسکریپت مشترک باید هر دو شکل را بخواند. یادآوری: stdin را یک بار کامل بخوانید و JSON نامعتبر را خطای هوک بدانید.

```text
# Claude Code: PreToolUse برای Write
{"session_id": "abc", "cwd": "/site", "hook_event_name": "PreToolUse",
 "tool_name": "Write",
 "tool_input": {"file_path": "/site/dist/app.js", "content": "..."}}

# Codex: PreToolUse برای apply_patch
{"session_id": "xyz", "cwd": "/site", "hook_event_name": "PreToolUse",
 "tool_name": "apply_patch",
 "tool_input": {"command": "*** Begin Patch\n*** Update File: .env\n..."}}
```

منابع: [مرجع هوک در Claude Code](https://code.claude.com/docs/en/hooks)، [مرجع هوک در Codex](https://learn.chatgpt.com/docs/hooks)

## 9. زبان پاسخ هوک: کد خروجی — دقیقهٔ 38 تا 43

- هوک با کد خروجی و stdout و stderr جواب میزبان را می‌دهد
- exit 0 یعنی ادامه، exit 2 یعنی رد یا بازخورد
- برای قاعدهٔ اجباری exit 2 بدهید؛ exit 1 در Claude Code جلوی هیچ کاری را نمی‌گیرد.

**راهنمای اجرا و بحث:** این رایج‌ترین اشتباه در نوشتن هوک است: برنامه‌نویس‌ها عادت دارند با exit 1 خطا بدهند، ولی در Claude Code کد 1 فقط خطای غیرمسدودکننده است و کار ادامه پیدا می‌کند. پیام stderr فقط در exit 2 به مدل می‌رسد. JSON روی stdout برای تصمیم دقیق‌تر است، مثل permissionDecision در PreToolUse یا additionalContext برای افزودن زمینه؛ برای شروع، exit 2 کافی است.

**میزبان فقط کد خروجی و دو جریان متن را می‌فهمد**

| خروجی | معنی | چه کسی پیام را می‌بیند؟ |
| --- | --- | --- |
| `exit 0` | موفق؛ ادامه بده | stdout در SessionStart و UserPromptSubmit به زمینهٔ مدل می‌رود |
| `exit 2` | رد یا بازخورد | stderr به مدل برمی‌گردد تا دلیل را بفهمد |
| `exit 1` یا کد دیگر | خطای غیرمسدودکننده در Claude Code | کار ادامه می‌یابد؛ فقط هشدار برای کاربر |
| JSON روی stdout | تصمیم دقیق‌تر | `permissionDecision`، `decision: block`، `additionalContext` |

## 10. فعال‌سازی در Claude Code — دقیقهٔ 43 تا 48

- هوک‌ها زیر کلید hooks در یکی از فایل‌های settings.json تعریف می‌شوند
- فرمان /hooks هوک‌های ثبت‌شده و منبع هرکدام را فقط نمایش می‌دهد
- کلید hooks را در settings.json بنویسید؛ /hooks فقط نمایش می‌دهد و ویرایش نمی‌کند.

**راهنمای اجرا و بحث:** جدول سه سطح تنظیم را نشان می‌دهد. برای کار تیمی .claude/settings.json را commit کنید تا هوک برای همه یکسان باشد. تغییر فایل تنظیمات معمولاً خودکار خوانده می‌شود؛ اگر اثر نکرد نشست را دوباره باز کنید. در حالت تعاملی هوک‌ها تا تأیید trust پوشه اجرا نمی‌شوند. برای خاموش کردن موقت همهٔ هوک‌ها کلید disableAllHooks وجود دارد. مسیر اسکریپت را با CLAUDE_PROJECT_DIR بسازید تا به cwd وابسته نباشد.

**هوک در Claude Code کجا تعریف می‌شود؟**

| فایل | دامنه | داخل Git؟ |
| --- | --- | --- |
| `~/.claude/settings.json` | همهٔ پروژه‌های تو | خیر |
| `.claude/settings.json` | این پروژه، برای کل تیم | بله |
| `.claude/settings.local.json` | این پروژه، فقط برای تو | خیر |
| `hooks/hooks.json` در پلاگین | هر جا پلاگین فعال باشد | همراه پلاگین |

منابع: [مرجع هوک در Claude Code](https://code.claude.com/docs/en/hooks)، [راهنمای هوک در Claude Code](https://code.claude.com/docs/en/hooks-guide)

## 11. مسیر یک تصمیم PreToolUse — دقیقهٔ 48 تا 52

- مدل تصمیم می‌گیرد ابزار را صدا بزند، ولی میزبان پیش از اجرا هوک را اجرا می‌کند
- هوک ابزار را رد می‌کند و دلیل همراه راه درست را برمی‌گرداند
- مدل متوقف نمی‌شود؛ با اطلاعات تازه مسیر را اصلاح می‌کند

**راهنمای اجرا و بحث:** این نمودار را با مثال واقعی آزمایشگاه بگویید: مدل می‌خواهد dist/app.js را مستقیم بنویسد. میزبان JSON رخداد را به guard.mjs می‌دهد، اسکریپت با exit 2 رد می‌کند و می‌نویسد «خروجی build است؛ منبع را ویرایش کن.» مدل همین پیام را می‌خواند و سراغ فایل منبع می‌رود. تأکید کنید پیام خطای خوب فقط نه نمی‌گوید، راه درست را هم نشان می‌دهد.

## 12. فعال‌سازی در Codex؛ hooks.json و اعتماد با /hooks — دقیقهٔ 52 تا 57

- هوک‌ها در 
- /.codex/hooks.json، در .codex/hooks.json پروژه یا در جدول hooks داخل config.toml تعریف می‌شوند
- هوک تازه یا تغییرکرده تا در /hooks بازبینی و trust نشود اجرا نمی‌شود
- فرمان با cwd نشست اجرا می‌شود؛ مسیر اسکریپت را از ریشهٔ git بسازید

**راهنمای اجرا و بحث:** مقایسه با Claude Code را پررنگ کنید: Codex اعتماد را برای هر تعریف هوک با hash آن ثبت می‌کند؛ اگر کسی یک خط هوک را تغییر دهد، تا بازبینی دوباره اجرا نمی‌شود. هوک‌ها به‌طور پیش‌فرض روشن‌اند و با hooks = false در بخش features خاموش می‌شوند؛ نام قدیمی codex_hooks هنوز به‌عنوان نام مستعار پذیرفته می‌شود. Codex متغیر محیطی مسیر پروژه ندارد؛ مستند رسمی ساختن مسیر با git rev-parse را پیشنهاد می‌کند.

```text
# .codex/hooks.json: همان ساختار Claude، زیر کلید hooks
{"hooks": {"PreToolUse": [{"matcher": "Edit|Write|Bash",
  "hooks": [{"type": "command",
    "command": "node \"$(git rev-parse --show-toplevel)/hooks/guard.mjs\""}]}]}}

# یا داخل ~/.codex/config.toml
[[hooks.PreToolUse]]
matcher = "^Bash$"
[[hooks.PreToolUse.hooks]]
type = "command"
command = 'node "$(git rev-parse --show-toplevel)/hooks/guard.mjs"'

# هوک‌ها پیش‌فرض روشن‌اند. خاموش کردن: [features] hooks = false
# در Codex: /hooks → بازبینی → trust
```

منابع: [مرجع هوک در Codex](https://learn.chatgpt.com/docs/hooks)، [مرجع config.toml در Codex](https://learn.chatgpt.com/docs/config-file/config-reference)

- PreToolUse پیش از Edit و Write مسیر فایل را بررسی می‌کند
- dist، .env، package-lock.json و خود پوشهٔ هوک‌ها قفل‌اند
- پیام خطا راه درست را هم می‌گوید: منبع را ویرایش کن و build بگیر

**راهنمای اجرا و بحث:** مثالی واقعی از همین مخزن دوره بزنید: content/course.json را اسکریپت author_content.py می‌سازد و هر ویرایش دستی آن در ساخت بعدی پاک می‌شود؛ دقیقاً جایی که یک هوک نگهبان ارزش دارد. نسخهٔ bash روی اسلاید فقط file_path را می‌خواند و برای Claude کافی است؛ نسخهٔ guard.mjs آزمایشگاه متن patch در Codex را هم می‌خواند. قفل کردن پوشهٔ هوک‌ها مانع می‌شود که عامل قانون خودش را تغییر دهد.

```text
#!/bin/bash
# PreToolUse با matcher "Edit|Write" در Claude Code
f=$(jq -r '.tool_input.file_path // empty')

```

## 14. خودکارساز: فرمت خودکار با Prettier — دقیقهٔ 62 تا 66

- PostToolUse بعد از هر ویرایش Prettier را روی همان فایل اجرا می‌کند
- دیگر لازم نیست در AGENTS.md بنویسید «کد را فرمت کن»
- وقتی خروجی exit 0 است مدل اصلاً متوجه هوک نمی‌شود و diff تمیز می‌ماند

**راهنمای اجرا و بحث:** این هوک جلوی چیزی را نمی‌گیرد و فقط کاری را خودکار انجام می‌دهد. ignore-unknown باعث می‌شود فایل‌هایی که Prettier نمی‌شناسد خطا ندهند. یادآوری: نمونهٔ روی اسلاید از jq و file_path استفاده می‌کند و مخصوص Claude Code است؛ برای Codex باید مسیرها را از متن patch استخراج کرد، همان کاری که lib.mjs انجام می‌دهد.

```text
"PostToolUse": [{
  "matcher": "Edit|Write",
  "hooks": [{"type": "command",
    "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write --ignore-unknown"}]
}]
```

## 15. حلقهٔ بازخورد: lint بعد از هر ویرایش — دقیقهٔ 66 تا 72

- مدل ویرایش می‌کند، lint خطا می‌گیرد و متن خطا با exit 2 به مدل برمی‌گردد
- مدل خطا را می‌خواند و خودش اصلاح می‌کند؛ هوک دوباره اجرا می‌شود تا تمیز شود
- مدل در یافتن خطای خودش ضعیف است ولی در رفع خطایی که به او نشان داده شود قوی است

**راهنمای اجرا و بحث:** اینجا معمولاً لحظهٔ فهم کلاس است. نمودار را قدم‌به‌قدم بگویید و تأکید کنید که شما هیچ دخالتی نکرده‌اید. مقایسه با دستور در AGENTS.md: هوک همیشه و بلافاصله بعد از هر ویرایش اجرا می‌شود، وقتی زمینه هنوز تازه است؛ دستور متنی معمولاً آخر کار و گاهی هرگز. quiet فقط error را گزارش می‌کند و head خروجی را کوتاه نگه می‌دارد تا توکن هدر نرود.

```text
#!/bin/bash
# PostToolUse: ویرایش انجام شده؛ فقط خطا را به مدل نشان بده
f=$(jq -r '.tool_input.file_path')
case "$f" in *.js|*.ts|*.jsx|*.tsx) ;; *) exit 0 ;; esac
out=$(npx eslint --quiet --format compact "$f" 2>&1) || {
  echo "$out" | head -20 >&2
  exit 2
}
```

## 16. جلوگیری یا اصلاح؛ PreToolUse در برابر PostToolUse — دقیقهٔ 72 تا 76

- exit 2 در هر دو رخداد معنای متفاوتی دارد
- در PostToolUse ویرایش قبلاً روی دیسک نوشته شده است
- exit 2 در PostToolUse چیزی را برنمی‌گرداند؛ فقط مشکل را به مدل نشان می‌دهد.

**راهنمای اجرا و بحث:** این معمولاً اولین سؤال کلاس است: «اگر PostToolUse رد کند، تغییر برمی‌گردد؟» پاسخ منفی است. یک نگهبان پیش از عمل جلوی آن را می‌گیرد؛ یک معلم پس از عمل اشکال را نشان می‌دهد. برای قفل امنیتی یا فایل حساس هرگز به PostToolUse تکیه نکنید، چون وقتی اجرا شود اثر قبلاً رخ داده است.

**یک کد خروجی، دو معنای متفاوت**

| موضوع | `PreToolUse` + exit 2 | `PostToolUse` + exit 2 |
| --- | --- | --- |
| ویرایش انجام شد؟ | خیر؛ جلوی آن گرفته شد | بله؛ روی دیسک است |
| معنی برای مدل | اجازه نداری | انجام دادی، مشکل دارد، درستش کن |
| نقش | نگهبان | معلم |
| مثال | قفل dist و .env | lint و فرمت |

## 17. دروازهٔ Stop: بدون build سبز تمام نکن — دقیقهٔ 76 تا 81

- Stop وقتی اجرا می‌شود که عامل می‌خواهد بگوید «تمام شد»
- اگر build یا تست شکست بخورد، exit 2 عامل را با متن خطا به کار برمی‌گرداند
- بدون بررسی stop_hook_active ممکن است حلقهٔ بی‌نهایت بسازید

**راهنمای اجرا و بحث:** قوی‌ترین مثال جلسه: عامل نمی‌تواند با build شکسته اعلام پایان کند. دام مهم را با سناریو بگویید: اگر build به دلیلی خارج از کنترل عامل شکسته باشد، هوک هر بار عامل را برمی‌گرداند. فیلد stop_hook_active در هر دو ابزار نشان می‌دهد این نوبت قبلاً یک بار با Stop ادامه داده شده است. Claude Code سقف داخلی برای ادامه‌های پیاپی هم دارد، ولی طراحی درست نباید به آن تکیه کند. در Codex خروجی موفق Stop باید JSON باشد؛ به همین دلیل اسکریپت آکولاد خالی چاپ می‌کند.

```text
#!/bin/bash
input=$(cat)
if [ "$(echo "$input" | jq -r '.stop_hook_active')" = "true" ]; then
  echo '{}'; exit 0        # بار دوم: اجازهٔ توقف، بدون حلقهٔ بی‌نهایت
fi
if ! npm run build > /tmp/build.log 2>&1; then
  tail -20 /tmp/build.log >&2
  exit 2                   # عامل با متن خطا به کار برمی‌گردد
fi
echo '{}'                  # Codex در exit 0 خروجی JSON می‌خواهد
```
