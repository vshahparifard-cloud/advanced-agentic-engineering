# پروژهٔ نهایی — دستیار نگهداری محتوای دوره
## سناریو
یک درخواست تغییر سرفصل دریافت می‌شود. عامل باید محتوای فعلی را از MCP بخواند، تصمیم قبلی را از حافظهٔ پروژه بازیابی کند، با یک درگاه محدود پاسخ بسازد و گزارش تغییر پیشنهادی را بدون انتشار خودکار تحویل دهد.
## قرارداد پذیرش
1. ورودی دارای project، job_id، commit SHA و درخواست محدود است.
2. مهارت review-evidence فقط برای کار مرتبط انتخاب می‌شود.
3. MCP فقط کاتالوگ عمومی را می‌خواند؛ ورودی نامعتبر رد می‌شود.
4. memory.at با tenant و تاریخ اعتبار فیلتر می‌کند؛ منبع پاسخ مشخص است.
5. درخواست مدل دارای سقف خروجی، timeout و سیاست fallback سازگار است.
6. گزارش شامل یافته، شاهد مسیر، آزمون و ریسک است؛ trace پالایش‌شده به job متصل است.
7. اجرای دوبارهٔ job موفق skipped می‌شود. timeout به unknown می‌رود و اثر بیرونی پیش از retry بررسی می‌شود.
## مسیر ساخت در طول دوره
جلسهٔ اول قرارداد؛ جلسهٔ دوم مهارت؛ جلسهٔ سوم ابزار کاتالوگ؛ جلسهٔ چهارم سیاست درگاه؛ جلسهٔ پنجم بازیابی زمانی؛ جلسهٔ ششم runner و بستهٔ تحویل. مدل قطعی آفلاین برای آزمایش قرارداد مجاز است ولی باید صریح معرفی شود.
## شواهد تحویل
یک README با فرمان راه‌اندازی، نسخه‌ها و وضعیت اتصال زنده؛ خروجی آزمون‌های قطعی؛ نمونهٔ درخواست و پاسخ؛ نمودار مرز اعتماد؛ یک شکست عمدی و مسیر recovery؛ برنامهٔ review برای head SHA مشخص. تمام داده‌ها مصنوعی باشند.

## پرسش دفاع
اگر مدل دوم قالب را رعایت نکرد چه می‌کنید؟ اگر خبر مالکیت دیر رسید، پرسش ماه قبل چگونه پاسخ می‌گیرد؟ اگر PR ساخته شد ولی پاسخ شبکه گم شد، retry چگونه از تکرار جلوگیری می‌کند؟
## توسعهٔ تولیدی
نمونه‌های این مخزن اجزای آموزشی قابل اجرا هستند. برای تولید به ledger مشترک، سیاست داده، OAuth شبکه‌ای، ارزیابی واقعی مدل‌ها و تست بار نیاز دارید. داشتن fixture یا config به معنی تأیید این سرویس‌های عملیاتی نیست.
