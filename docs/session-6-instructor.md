# راهنمای مدرس — عامل‌های Headless و اتوماسیون عملیاتی

مدت: ۱۲۰ دقیقه؛ هر اسلاید ۵ دقیقه. فعالیت‌های عملی در زمان همین اسلایدها انجام می‌شوند، نه علاوه بر آن. پیش از کلاس نصب ابزارها را طبق راهنمای آزمایشگاه انجام دهید.

در صورت نیاز به استراحت، پنج دقیقه از بخش بحث پایانی کم کنید و آن را در زمان جلسه ثبت کنید.

## 1. تعریف کار Headless — دقیقهٔ 0 تا 5

- ورودی، اختیار و معیار پایان از پیش مشخص‌اند
- نبود رابط تعاملی نیاز به کنترل بیشتر دارد
- خروجی ساخت‌یافته و کد خروج باید بررسی شوند

**راهنمای اجرا و بحث:** کار نمونه تهیهٔ گزارش بازبینی است، نه merge خودکار. این انتخاب امکان اجرای کم‌خطر و بررسی انسانی را می‌دهد. خطای ورود باید سریع و قابل تشخیص تمام شود.

## 2. Codex غیرتعاملی — دقیقهٔ 5 تا 10

- codex exec یک کار محدود را اجرا می‌کند
- --json جریان رخداد می‌دهد
- --output-schema شکل گزارش نهایی را محدود می‌کند

**راهنمای اجرا و بحث:** فرمان‌ها را با سند جاری مقایسه کنید. schema خروجی جای آزمون صحت ادعاها را نمی‌گیرد. در این دوره مجوز read-only برای گزارش‌گیری کافی است.

## 3. Claude غیرتعاملی — دقیقهٔ 10 تا 15

- claude -p متن را بدون نشست تعاملی می‌گیرد
- --output-format json خروجی ماشینی می‌دهد
- مجوز ابزارها را صریح و محدود تعیین کنید

**راهنمای اجرا و بحث:** نمونهٔ خواندنی را اجرا یا نمایش دهید. تنها exit code را نسنجید؛ در خروجی JSON وضعیت خطای اجرا را هم بررسی کنید. برای نوشتن فایل یا Bash اختیار اضافه را آگاهانه بدهید.

## 4. اشتراک و API یکسان نیستند — دقیقهٔ 15 تا 20

- CLI محلی می‌تواند از ورود رسمی حساب پشتیبانی‌شده استفاده کند
- Codex exec احراز هویت ذخیره‌شده را استفاده می‌کند
- برای CI از مسیر رسمی مناسب همان حساب استفاده کنید

**راهنمای اجرا و بحث:** اشتراک را به proxy غیررسمی API تبدیل نکنید. توکن مرورگر را استخراج نکنید. کلید API، credential سازمانی و ورود تعاملی مسیرهای جدا با سیاست و صورتحساب جدا هستند.

## 5. اجرای اشتراکی با حدود روشن — دقیقهٔ 20 تا 25

- میزبان مورد اعتماد و حساب واجد شرایط لازم است
- انقضای ورود و سقف مصرف باید مدیریت شود
- SDK شخص ثالث را خودکار مجاز به استفاده از OAuth اشتراک ندانید

**راهنمای اجرا و بحث:** این درس فقط CLI رسمی را آموزش می‌دهد. برای Claude ورود رسمی و مستندات حساب را بررسی کنید؛ مجوز استفادهٔ SDK یا سرویس چندکاربره از آن نتیجه نمی‌شود.

## 6. CI بدون انتظار برای سؤال — دقیقهٔ 25 تا 30

- credential در secret store قرار می‌گیرد
- فرمان نباید برای login یا approval منتظر بماند
- نبود credential باید fail-fast شود

**راهنمای اجرا و بحث:** workflow انتشار سایت به مدل احتیاج ندارد. نمونهٔ اجرای عامل در راهنمای جلسه جدا و غیرفعال است تا forkها به secret یا هزینهٔ ناخواسته وابسته نباشند.

## 7. قرارداد job — دقیقهٔ 30 تا 35

- job_id، ورودی و حداکثر زمان مشخص‌اند
- وضعیت running، succeeded، failed یا unknown ثبت می‌شود
- گزارش و log خروجی‌های مستقل‌اند

**راهنمای اجرا و بحث:** فایل runner.py را نشان دهید. نام کار از ورودی shell ساخته نمی‌شود و فرمان با آرایه اجرا می‌شود. timeout گروه فرایند را متوقف می‌کند و وضعیت unknown را برای بررسی اثر خارجی می‌نویسد.

## 8. Idempotency — دقیقهٔ 35 تا 40

- کلید ثابت کار تکرار ناخواسته را تشخیص می‌دهد
- نتیجهٔ موفق دوباره اجرا نمی‌شود
- کار failed فقط با retry صریح دوباره اجرا می‌شود

**راهنمای اجرا و بحث:** اجرای دوبارهٔ demo را نشان دهید. شمارنده نباید دوبار اثر بگذارد. برای سرویس چندworker به قفل یا ledger مشترک نیاز دارید؛ فایل محلی برای یک runner آموزشی است.

## 9. زمان‌بندی درست — دقیقهٔ 40 تا 45

- cron روی runner منطقهٔ زمانی مشخص دارد
- اجرای همپوشان باید محدود شود
- زمان‌بندی با تضمین اجرای دقیق در ثانیه یکسان نیست

**راهنمای اجرا و بحث:** cron نمونه را UTC معرفی کنید و تبدیل زمان محلی را جدا بنویسید. GitHub scheduled workflow ممکن است تأخیر داشته باشد؛ برای SLA سخت از scheduler مناسب استفاده کنید.

## 10. GitHub و GitLab — دقیقهٔ 45 تا 50

- PR و MR هر دو باید با شاخه و commit مشخص بررسی شوند
- گزارش روی head قدیمی نباید معتبر شمرده شود
- اختیار نوشتن و merge از اختیار خواندن جداست

**راهنمای اجرا و بحث:** فایل review_plan.py URL یا diff را اجرا نمی‌کند؛ فقط دادهٔ JSON اعتبارسنجی‌شده را به برنامهٔ بازبینی تبدیل می‌کند. فرمان‌های gh و glab در راهنما برای حساب مجاز آمده‌اند.

## 11. معماری اتوماسیون امن — دقیقهٔ 50 تا 55

- scheduler کار را به runner محدود می‌دهد
- عامل روی checkout مشخص گزارش می‌سازد
- دروازهٔ آزمون و بازبینی، اقدام نوشتنی را جدا می‌کند

**راهنمای اجرا و بحث:** مسیر recovery را روی نمودار توضیح دهید. نتیجهٔ نامعلوم نباید موفق گزارش شود. انتشار سایت نمونه یک کار قطعی است و با اجرای خود عامل متفاوت است.

## 12. نمایش زنده: runner قطعی — دقیقهٔ 55 تا 60

- demo بدون حساب مدل اجرا می‌شود
- بار دوم همان job به‌صورت skipped برمی‌گردد
- فرمان شکست‌خورده وضعیت failed ثبت می‌کند

**راهنمای اجرا و بحث:** python labs/session-6/runner.py را اجرا کنید. فایل state در پوشهٔ موقت آزمایشگاه است و در Git ثبت نمی‌شود. محتویات state نباید secret داشته باشد.

## 13. آزمایشگاه: خروجی ساخت‌یافته — دقیقهٔ 60 تا 65

- report.schema.json را بخوانید
- گزارش باید findings، tests و status داشته باشد
- یافتهٔ بدون مسیر و شاهد پذیرفته نیست

**راهنمای اجرا و بحث:** یک گزارش مصنوعی با دو یافته بسازید. شدت بالا را بدون بازتولید نسبت ندهید. schema نمونه حداقل شکل داده را می‌سنجد؛ بازبین انسانی اعتبار یافته را بررسی می‌کند.

## 14. آزمایشگاه: اجرای محدود CLI — دقیقهٔ 65 تا 70

- فرمان read-only در راهنما را در مخزن تمرینی اجرا کنید
- stdout و stderr را جدا نگه دارید
- گزارش نهایی را با schema تطبیق دهید

**راهنمای اجرا و بحث:** اگر حساب در دسترس نیست، fixture آفلاین همان مسیر parser را می‌سنجد. این را اجرای زنده معرفی نکنید. برای CLI واقعی پیش از شروع نسخه و login status را ثبت کنید.

## 15. آزمایشگاه: شکست و timeout — دقیقهٔ 70 تا 75

- فرمان fixture با خروج غیرصفر را اجرا کنید
- فرمان کند باید در مهلت تعیین‌شده به unknown برود
- هیچ‌کدام نباید succeeded ثبت شوند

**راهنمای اجرا و بحث:** آزمون خودکار این حالات را پوشش می‌دهد. اگر فرایند فرزند تولید می‌کند، گروه فرایند باید متوقف شود. kill کردن تنها والد می‌تواند کار پنهان باقی بگذارد.

## 16. آزمایشگاه: بازیابی پس از وقفه — دقیقهٔ 75 تا 80

- state با running قدیمی را به unknown تبدیل کنید
- پیش از retry اثر خارجی احتمالی را بررسی کنید
- retry صریح باید در گزارش قابل تشخیص باشد

**راهنمای اجرا و بحث:** در نسخهٔ آموزشی قفل محلی مانع اجرای همزمان می‌شود. state نیمه‌کاره به معنی شکست قطعی عملیات خارجی نیست. از فراگیر بخواهید برای انتشار PR شاهد بررسی بیرونی پیشنهاد دهد.

## 17. آزمایشگاه: برنامهٔ PR و MR — دقیقهٔ 80 تا 85

- fixtures دو میزبان را به قرارداد مشترک تبدیل کنید
- head SHA و فایل‌های تغییرکرده را ثبت کنید
- خروجی فقط برنامهٔ review باشد

**راهنمای اجرا و بحث:** python review_plan.py را روی هر دو fixture اجرا کنید. هیچ پیام یا merge در تمرین انجام نمی‌شود. هدف جلوگیری از اشتباه بین شمارهٔ PR، URL و commit واقعی است.

## 18. امنیت PR از fork — دقیقهٔ 85 تا 90

- کد PR ورودی غیرقابل اعتماد است
- secret را به اجرای کد ناشناس ندهید
- pull_request_target همراه checkout کد مهاجم خطرناک است

**راهنمای اجرا و بحث:** مدل تهدید را با یک package script مخرب نشان دهید. محدود کردن prompt جلوی اجرای script نصب را نمی‌گیرد. محیط اجرای کد باید جدا و بدون secret باشد.

## 19. ثبت شواهد و نگهداری — دقیقهٔ 90 تا 95

- لاگ با run ID و commit SHA مرتبط است
- secret و دادهٔ خصوصی پیش از ذخیره حذف می‌شوند
- artifact مدت نگهداری مشخص دارد

**راهنمای اجرا و بحث:** workflow سایت artifact را با deploy-pages منتشر می‌کند. گزارش عامل عمومی نباید حاوی توکن، prompt خصوصی یا متن کامل issue خصوصی باشد. حداقل شواهد لازم را نگه دارید.

## 20. دروازهٔ اقدام بیرونی — دقیقهٔ 95 تا 100

- آزمون و review پیش از نوشتن لازم‌اند
- commit بررسی‌شده باید با commit مقصد یکی باشد
- merge و انتشار پیام به اختیار روشن نیاز دارند

**راهنمای اجرا و بحث:** مسئلهٔ TOCTOU را توضیح دهید: پس از review، شاخه تغییر کرده است. پیش از اقدام، head را دوباره بررسی کنید. گزارش قدیمی را برای commit جدید معتبر فرض نکنید.

## 21. محدودیت هزینه و توقف — دقیقهٔ 100 تا 105

- زمان، تعداد تلاش و مصرف را محدود کنید
- خطای auth با retry بی‌نهایت حل نمی‌شود
- در توقف، وضعیت و قدم بعدی را حفظ کنید

**راهنمای اجرا و بحث:** سه خطای متوالی ورود را مثال بزنید. job باید fail-fast و نیاز به اقدام را روشن گزارش کند. افزایش دسترسی یا استخراج credential راه بازیابی قابل قبول نیست.

## 22. Runbook بازیابی — دقیقهٔ 105 تا 110

- تشخیص ← توقف تکرار ← بررسی اثر ← بازیابی ← تأیید
- نسخهٔ سالم و artifact قبلی را نگه دارید
- پس از incident آزمون بازگشت اضافه کنید

**راهنمای اجرا و بحث:** سناریوی انتشار ناقص را با کلاس حل کنید. ابتدا مشخص کنید نسخهٔ قبلی هنوز سالم است یا نه. بازاجرای کور workflow ممکن است علت اصلی را پنهان کند.

## 23. سنجش: وضعیت نامعلوم — دقیقهٔ 110 تا 115

- timeout اثبات نمی‌کند اثر خارجی رخ نداده است
- پیش از retry باید مقصد بررسی شود
- idempotency برای عملیات قابل تکرار طراحی می‌شود

**راهنمای اجرا و بحث:** از فراگیر بخواهید تفاوت failed و unknown را با مثال ایجاد PR توضیح دهد. اگر پاسخ API گم شده باشد، ممکن است PR ساخته شده باشد. جستجو با شناسهٔ کار پیش از تکرار ضروری است.

## 24. تحویل نهایی ۱۲ ساعت — دقیقهٔ 115 تا 120

- قرارداد عامل، مهارت، MCP، gateway، حافظه و runner
- آزمون‌های قطعی و شواهد اجرای زنده را جدا ارائه کنید
- محدودیت‌ها، هزینه و recovery در README ثبت شوند

**راهنمای اجرا و بحث:** پروژهٔ نهایی یک دستیار نگهداری دوره است که فقط پیشنهاد تغییر می‌دهد. rubric صد امتیازی در سیلابس آمده است. هر گروه یک شکست عمدی و مسیر بازیابی خود را نیز نمایش دهد.
